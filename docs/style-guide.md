# 技术文档写作规范

[English](style-guide.en.md) | 简体中文

本规范用于编写 XDRemux 的产品说明、研究记录和维护步骤。当前双语文档以英文为原稿，再同步相同技术内容的中文版本。

## 依据与适用范围

英文技术文档采用 [ASD-STE100 Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf) 的写作规则。该版发布日期为 2025 年 1 月 15 日。PDF 地址变化时，从[官方获取页面](https://www.asd-ste100.org/STE_downloads.html)查找。

中文采用 Fenng 的 [Tech-Doc-Style-Chinese Skill](https://github.com/Fenng/Tech-Doc-Style-Chinese/blob/b119d01c9bb7cd132b3c62fafdff34227c4410d1/SKILL.md)及其[受控中文技术写作规则](https://github.com/Fenng/Tech-Doc-Style-Chinese/blob/b119d01c9bb7cd132b3c62fafdff34227c4410d1/references/controlled-technical-chinese.md)。这些规则按中文句法调整受控语言方法，不把英语词典和词数限制直接套到中文句子上。

XDRemux 不声明正式符合 ASD-STE100。风格检查器不能认证术语、技术事实或全文对标准的符合程度。

仓库的 [pstack 流程](../.agents/skills/pstack-workflow/SKILL.md)组织源码核对、分组修改、验证和独立审阅。项目 Skill 保留已有上游来源记录，不依赖 Cursor，也不额外授予外部操作权限。

## 先保留含义，再调整风格

按以下优先级处理冲突：

1. 保留事实、要求、法律含义、警告和证据边界。
2. 遵守用户指定范围及仓库现有约定。
3. 保留标识符、数值、单位、命令和引用原文。
4. 改善信息顺序、句子和术语。
5. 修正标点、留白及 Markdown 格式。

行为说明必须对应代码、测试或已有验证记录。旧文档和待合并 PR 不能证明当前行为。假设、历史观察和已支持功能必须明确区分。

## 确定文档用途

| 用途 | 必要内容 |
| --- | --- |
| 入口页 | 支持的任务、前置条件、重要限制和下一步入口。 |
| 操作步骤 | 前置条件、操作前的风险提示、执行顺序、预期结果及失败处理。 |
| 参考文档 | 准确的命令、类型、取值、默认值、单位、互斥关系、输出和错误。 |
| 原理说明 | 一个明确主题、对应的实现模块和设计取舍。 |
| 研究记录 | 输入、方法、测量结果、不确定性及进一步验证的条件。 |

用标题或链接区分参考资料和较长操作步骤。不要在每份文档中重复完整命令约定。

## 英文操作与说明

按内容采用 ASD-STE100 第 1 部分的规则：

- 同一对象使用同一技术名词。标准词汇保持规定词义和词性。
- 保留软件和成像领域必要的技术名词、技术动词，不把黑话当作专业术语。
- 使用主动语态和直接动词。操作步骤使用祈使句。
- 每句只给一个指令；必须同时执行的动作可以保留在同一句。
- 条件先于依赖该条件的动作。覆盖文件的命令前必须说明数据丢失风险。
- 按标准的计数规则，英文操作句最多 20 词，说明句最多 25 词。
- 每段只说明一个主题。英文说明段落最多 6 句。
- 保留冠词及完整句子所需的连接词。句子过密时重新组织，不删除必要条件。
- 避免过长的名词组合和歧义指代。必要时重复对象名称。
- 使用美式拼写。避免分号、习语、宣传用语及无依据的质量或速度主张。

`must` 表示要求，`can` 表示能力，`may` 表示可能性。不要把有限条件下的观察改成要求或保证。

## 中文说明

英文技术内容定稿后，用自然中文表达相同含义。要求、默认值、例外和不确定性必须一致。

- 翻译解释性文字。API、框架、命令选项、元数据键、路径等标识符保持准确。
- 同一概念使用一个首选中文术语。必要的英文术语在首次出现时解释。
- 每句保留清楚的主语或动作。拆开无关动作，但不要拆散条件与动作的关系。
- 正文使用中文标点，新写的引用使用「」；固定引用和代码保持原样。
- 中文与英文、阿拉伯数字或行内代码之间保留一个半角空格。中文标点两侧不加空格。
- 正文在源文件中一段一行。代码块、表格、显式换行和引用记录保留结构。
- 标题直接说明任务或主题。能列出具体检查时，不用「闭环」等模糊词代替。

不要把 `Motion Photo` 和 `Live Photo` 翻译成可互换的格式名。两者都可以泛称实况照片，但容器结构和验证约定不同。

涉及模块所有权时，写清模块职责，不创造新的产品组件名称。需要定位代码时保留 crate 名。

## 区分文档类别

当前用户指南、开发指南、质量政策、模型卡和维护说明描述现行代码。英文和中文必须在同次修改中同步。原本没有中文版的 Agent Skill 可以保留英文。

历史记录保留测量值、原始命令、路径和结论。实现变化时更新当前摘要，通过范围说明或勘误解释差异，不替换原始证据正文。发布说明描述对应版本，不描述当前分支。

生成的输出和机器可读内容必须保留准确拼写。JSON 键、元数据字段、文件名、样本哈希、版权声明和许可证正文保持原样。只有源码证据表明命令需要修正时，才修改代码示例。

## 检查文档修改

1. 确认修改文件及其文档类别。
2. 将每项修改后的主张与代码、测试或证据记录对照。
3. 核对双语范围、默认值、警告和限制。
4. 检查本地链接、锚点、命令名和选项。
5. 运行现有文档与目录结构检查。
6. 复核最终差异，查找丢失的条件和误改的机器可读内容。

中文 Skill 的 `lint_copy_rules.py` 可补充措辞和排版提示。警告需要结合语境判断，不能据此修改代码标识符或历史记录。
