# 待预处理的 Cinematic MOV

[English](cinematic.en.md) | 简体中文

`xdremux convert --apple-cinematic` 从普通视频生成新的待预处理 Cinematic MOV。发布前，输出必须达到 Apple 公共 API 的 `needsPreprocessing` 状态。现有证据不能证明推理效果与原始相机效果相同。

## 命令与运行条件

```bash
xdremux convert --input ordinary.mp4 --output pending.mov --apple-cinematic
```

`convert` 和 `batch` 都支持 `--apple-cinematic`。它不能与照片功能开关或 `--oppo-compatible` 同时使用。输出必须采用 `.mov` 扩展名，且文件尚不存在。单文件转换未指定输出时，命令会在源文件旁生成 `SOURCE.xdremux.mov`。

[Rust 运行时](../crates/xdremux-runtime/src/lib.rs)在生成前后计算源文件哈希。源文件发生变化时，运行时会拒绝输出。候选文件通过硬链接发布，不能替换已有输出。

当前实现需要 macOS 27 或更新版本、macOS 27 SDK 构建及可用的 Apple 推理资源。它还需要[原生适配器](../Sources/XDCinematicNative/cinematic_envelope.m)使用的 Portrait/Cinematic 私有方法。适配器在调用每个必要的私有 Objective-C 方法前检查其类型编码。方法、SDK、系统或资源不受支持时，命令会失败。旧 SDK 构建保留其他适配器操作，但会在推理前拒绝 Cinematic 生成。

| 参数 | 默认值 | 允许范围 | 含义 |
| --- | --- | --- | --- |
| `--focal-length-35mm MM` | `24` | `1` 到 `300` | 每帧使用的焦距假设 |
| `--aperture F` | `2.8` | `1` 到 `64` | 光圈假设 |

两个值都必须是有限数值。显式传入任一参数时，都必须指定 `--apple-cinematic`。源文件缺少相机几何信息时，这些值是生成元数据所用的拍摄假设，不是实测光学属性。

### 已记录的兼容性结果

此命令处于实验阶段。`needsPreprocessing` 和资源状态 `ready` 表示 Apple 能识别元数据，不能证明后续预处理支持每种输入。

项目此前在 macOS 27.0.1 上记录了以下结果：

| 输入 | 结果 |
| --- | --- |
| 移除 Cinematic 数据的 1080p/4K HEVC 相机输入 | 公共预处理、渲染和编辑重载通过 |
| 独立编码的 1080p H.264 | 公共预处理、渲染和编辑重载通过 |
| 内容匹配的 1920×1080、30 fps 短片，分别采用 H.264、HEVC 和 ProRes Standard | 三种编码均通过公共处理流程 |
| 独立编码的 640×360 H.264 | 待处理文件生成成功；预处理返回 `CNCinematicErrorDomain` 错误码 `5`（`unsupported`） |

这些检查说明，已测试的公共处理流程不要求 HEVC。修改色彩标签或虚拟传感器元数据没有消除 640×360 输入的拒绝。命令保留压缩媒体，不通过缩放或转码绕过该限制。其他尺寸、编码、系统及 iPhone Photos 行为需要单独验证。

## 处理所需的信息

推理流程先解码视频。编码受支持还不足以完成处理，文件还需要有效的 Cinematic 元数据封装。已测试的公共处理流程使用以下信息：

| 信息 | 要求 |
| --- | --- |
| 全局 `com.apple.quicktime.cinematic-video` 数据块 | 描述 Cinematic 媒体 |
| 逐帧摄制数据（cinematography） | 包含有效的检测 ID 和对焦决策 |
| 逐帧渲染数据（rendering） | 包含相机几何假设 |
| 视频与元数据时间 | 描述相同的可见时间线 |

`needsPreprocessing` 不要求已有栅格视差轨道。

### 停用元数据键的诊断实验

诊断实验通过重命名键来停用字段，同时保持媒体字节和容器偏移不变。停用摄制数据后，能力变为 `none`。停用全局数据块后，媒体仍处于待处理状态，但资源未就绪。停用逐帧渲染数据后，待处理媒体的资源虽已就绪，处理仍失败。因此，待处理分类不能验证所有处理输入。

另一项实验在 1080p H.264 短片中同时停用了多个键。这些键描述可识别的意图、`metadata.1`、光圈/视差标量和场景照度。公共预处理、渲染和编辑重载仍通过。保留的渲染数据和脚本包含各自的数值。只有自动对焦轨道和一个起始决策的脚本也通过。

生产输出保留这些字段。上述实验没有建立 Photos 所需的最小数据结构。编码本身不能恢复物理自动对焦、原始相机标定或缺失深度。

## 原生生成流程

Rust CLI 是产品入口。Swift/Objective-C 适配器执行 Apple 框架操作。生成的 MOV 是独立文件。

### 解码与选择主体候选

AVFoundation 解码选定的彩色视频轨道。`PTMonocularDisparityProvider` 根据每个解码帧和假设焦距推理临时视差。Vision 接收视频的显示方向，检测矩形随后映射回编码坐标。

主体候选按以下顺序选择：

1. 使用检测到的人脸。
2. 如果没有人脸，则检测上半身和人体姿态关节点。
3. 如果没有人体候选，则使用动物识别和猫、狗头部关键点。
4. 如果仍没有主体候选，则使用对象显著性检测。

| 候选 | 条件与几何规则 |
| --- | --- |
| 根据人体姿态生成的头部候选 | 双耳置信度均需至少达到 `0.3`。使用双耳中点，宽度取水平耳距的 `1.4` 倍。归一化宽度必须在 `0.01` 到 `0.5` 之间。按已定向图像的宽高比表示显示像素中的正方形区域。优先保留最多两个头部候选，否则使用上半身候选。 |
| 动物头部 | 识别出的猫、狗标签置信度需至少达到 `0.5`。头部关键点必须匹配到识别出的身体。鼻子及至少一只眼睛的置信度需至少达到 `0.3`。至少需要三个可靠头部点，且头部框至少 `60%` 的面积位于身体框内。条件不满足时，使用身体候选。 |
| 对象显著性区域 | 选择置信度最高的区域。置信度需至少达到 `0.3`，面积需占画面的 `0.5%` 到 `60%`。检测类型为 `unknown`，不表示识别出了人物。 |

### 跟踪主体与生成对焦决策

只要边界和置信度有效，公共 `CNObjectTracker` 就会延续最多两个主体。检测器短暂漏检时，跟踪仍可继续。新主体获得新的轨道和分组。各轨道保持自身的检测类型。

动物匹配同时使用头部和身体区域，区分猫、狗身份与通用显著性区域。只要跟踪器仍有效，姿态检测缺失就不会移除正在跟踪的动物头部。动物部位再次出现时，生成器会复用该主体分组中对应部位的轨道 ID。人体检测类型发生变化并重新建立跟踪时，会创建新轨道。匹配到的人体或动物头部检测区域用于校正跟踪漂移。

选择规则先优先考虑人体候选。随后，如果检测到的头部面积超过当前选中矩形面积的 `1/0.6` 倍，该头部可以接管焦点。否则，继续选择仍有效的当前主体。没有主体时，生成器选择画面中心的自动对焦区域。

自动对焦轨道独立于主体轨道。拍摄轨道和焦点使用各自的分配器命名空间，为公共编辑保留可用的 ID。每次主体切换都会生成一个基础决策。`PTCinematographyPostcaptureRefinement` 生成并序列化脚本。转焦期间，细化后的焦点检测对象与帧头保持一致。基础选择单独存储。

### 写入元数据与发布 MOV

生成器写入新的全局 Cinematic 元数据，并为每个解码帧写入一组逐帧元数据。字段值如下：

| 字段 | 值 |
| --- | --- |
| 未知的拍摄对焦/视差 | 原生待处理标记 `-1` |
| 可见裁切 | `(1,1)`，使 Apple 解析器保留逐帧假设焦距 |
| 虚拟传感器区域 | 编码图像尺寸 |
| 光圈 | 同时写入脚本和逐帧渲染数据 |
| 全局渲染配置 | 兼容的虚拟拍摄配置，渲染版本为 `5` |

生成器复制压缩视频及所有受支持的音轨，保留视频变换和轨道时间基。元数据生成后，生成器丢弃临时推理缓冲。输出不包含栅格视差轨道，也不复制原生样本的 Cinematic 载荷。

发布前，公共 `CNAssetInfo` 必须确认三个条件：能力为 `needsPreprocessing`、资源状态为 `ready`，且 `isPreprocessed == false`。

### 推理拍摄数据的限制

硬件/传感器字段和虚拟传感器区域是合成值。场景照度是从亮度推导的代理值。这些值不能恢复相机标定、防抖裁切或原始对焦选择。

输入的焦距假设保持不变。生成器不从图像运动推理光学变焦或绝对视场角。原始 Cinematic 几何、视差图和对焦决策仅作为诊断参考。主体连续性使用独立的选择规则，不复现 Apple 封闭的自动选焦算法，也不保证原始对焦决策一致。

## 验证

私有样本可以保留在 Git 外。在仓库根目录运行以下命令。结果目录必须尚不存在，构建目录可以新建或复用。

```bash
python3 scripts/apple/verify_cinematic_envelope.py \
  --input /absolute/path/native.MOV \
  --run-dir /absolute/path/new-results \
  --swift-build-dir /absolute/path/swift-build \
  --rust-build-dir /absolute/path/rust-build \
  --synthetic --compare-render --verify-batch
```

[验证脚本](../scripts/apple/verify_cinematic_envelope.py)构建当前 CLI 和适配器。对每个原生样本，脚本移除全局元数据以及所有非视频、非音频轨道。公共 `CNAssetInfo` 必须将所得普通副本的能力判定为 `none`。随后，脚本调用 CLI，生成独立的待处理元数据封装。

| 参数 | 附加行为 |
| --- | --- |
| 重复 `--input` | 添加原生样本 |
| `--verify-batch` | 对受支持的普通副本和合成输入执行目录发现及并行 `batch --apple-cinematic`。检查每个输出的 MOV 结果类型、媒体包一致性、公共预处理、渲染和编辑重载。 |
| `--no-previews` | 省略可重新生成的 PNG，保留数值证据 |
| `--automatic-reference` | 在内存中删除原生用户决策。使用所得基础脚本焦点渲染，并记录该参考模式。 |
| `--synthetic` | 添加没有原始 Cinematic 数据或可检测人脸的独立 1080p 和 360p H.264 输入 |

### 公共消费者与媒体检查

公共消费者检查包含以下内容：

| 类别 | 检查内容 |
| --- | --- |
| 脚本身份 | 拍摄 ID 命名空间、选定检测对象的轨道能否解析、各轨道检测类型是否稳定 |
| 帧与时间 | 逐帧焦点是否有限、帧数、时间戳、基础决策数量、焦距时间线 |
| 渲染元数据 | 光圈、逐帧键、渲染帧属性、虚拟传感器几何、逐帧焦距范围 |
| 资源状态 | 待处理资源状态；编辑前完成预处理 |
| 公共编辑 | 新增两个固定焦点轨道，且其 ID 与拍摄 ID 不冲突 |

FFprobe 比较逐个编码视频/音频包的哈希、时间戳和音频裁切数据。AVAssetReader 的音频缓冲分组不能证明媒体包相同。验证脚本在每项操作后复查源文件哈希。

使用 `--compare-render` 时，合成的 1080p 输入必须通过完整原生处理检查。360p 输入单独用于探测兼容性。只有 Apple 明确的预处理 `unsupported` 错误会记录为限制，其他错误会使验证失败。不受支持的样本不能提供渲染或编辑证据。后续系统若支持该样本，则继续执行完整渲染和编辑检查。

### Photos 消费者检查

1. 将待处理 MOV 导入 Photos 测试图库。
2. 开启电影效果。
3. 等待 Photos 处理资源。
4. 调整光圈和焦点。
5. 保存编辑，然后重新打开。
6. 验证渲染效果发生变化。

公共预处理和脚本重载不能替代这项检查。普通源文件没有 Cinematic 音频元数据。命令保留其音频样本，但不生成 Apple 的电影模式音频混音效果。

## 无界面的效果比较

`--compare-render` 通过公共 `CNAssetInfo` 分别预处理原生媒体和重新生成的媒体，两者都必须变为 `renderable`。随后，公共 `CNRenderingSession` 使用 export 质量渲染。在共同时间范围的 `25%`、`50%` 和 `75%` 位置，分别以 f/2 和 f/16 采样。两份媒体使用相同的解码色彩、时间戳、10 位输入格式、输出几何和单位显示变换。

### 编辑与重载

预处理后，工具向生成的媒体添加两个公共自定义检测轨道和对焦决策。工具修改光圈，序列化 `CNScript.Changes`，然后重新加载。检查包含轨道 ID 无冲突、已保存的检测对象与时间戳、有限的逐帧焦点、光圈，以及两个编辑决策时刻的焦点。

公共加载器会重新计算转焦，原生相机对照也有此行为。工具记录其间焦点曲线的差异，不要求这些转焦与即时内存曲线完全相同。

合成输入没有原生参考，但同样执行预处理、export 渲染和编辑重载检查。平坦场景不要求可测量的虚化变化。单独检查生成文件时，使用渲染器的 `--verify-generated GENERATED.mov NEW_OUTPUT_DIRECTORY`。

### 测量空间与指标

测量使用完整分辨率的 `RGBA16Float` 纹理 RGB 数值，不包含 alpha。原生 RGBA 输出保留源传递函数。对于 HLG 输入，数值是 HLG 编码的 BT.2020 RGB。工具另外将渲染图像转换为扩展线性 BT.2020，并分别报告线性测量与保留源传递函数的测量结果。

解码色彩平面的哈希必须相同。原生与推理深度栅格尺寸不同时，工具分别验证两份栅格，并将深度差异标为不可直接比较。两份媒体仍按不变的彩色视频分辨率渲染。

| 证据 | 记录的值 |
| --- | --- |
| 渲染差异 | 像素是否完全相同、平均绝对误差、均方根误差、峰值信噪比，以及绝对差大于 `0.001` 的分量比例 |
| 深度与虚化效果 | 推理视差及 f/2 与 f/16 的效果，分别测量完整画面和原生对焦矩形 |
| 效果位置 | 效果余弦相似度，用于判断虚化变化是否发生在相近区域 |
| 可重复性 | 重复渲染原生媒体 |
| 完整处理脚本 | 每帧的检测 ID、分组、类型、矩形、焦点、基础决策时刻和转焦范围 |

原始检测 ID 属于各自的媒体，不能用于标识不同媒体中的同一主体。使用原生焦点数值渲染生成版本，仅构成诊断对照。视差的缩放和偏移没有定义，相同数值不能证明不同视差图使用相同的物理对焦平面。

### 比较验证结果

使用[比较工具](../scripts/diagnostics/compare_cinematic_alignment.py)比较新旧两轮验证结果：

```bash
python3 scripts/diagnostics/compare_cinematic_alignment.py \
  --baseline /absolute/path/baseline/report.json \
  --current /absolute/path/current/report.json \
  --output /absolute/path/current/alignment.json \
  --require-improvement SAMPLE_NAME --minimum-reduction 0.25
```

当前报告必须对应 `HEAD`，输出文件必须尚不存在。工具检查源文件哈希、普通输入完整性、媒体包一致性、解码色彩一致性、采样时间和参考焦点模式。它还检查渲染设置、原生渲染可重复性，以及参考效果能量是否不变。

对于 `SAMPLE_NAME`，平均 f/2 渲染误差和平均相对效果误差都必须至少下降 `25%`。报告包含其他所有样本，也包含退步的样本。测得改进不能证明效果等同。

此前的报告将未经转换的纹理数值错误标注为 `raw linear RGB`。与当前编码 RGB 测量进行比较时，必须保证解码色彩哈希相同且原生参考效果能量不变。工具会记录这项标注修正。此前将 HLG 纹理解释为线性 sRGB 的 PNG 预览不是有效的视觉参考。

### SDR 预览与 HDR 色彩回归

PNG 文件是 SDR 预览。Core Image 使用解码缓冲的色彩空间、内容亮度余量和平均亮度。`CISystemToneMap` 以显示亮度余量 `1` 映射到标准动态范围。工具将源视频的显示变换从视频坐标转换到 Core Image 坐标，并写入含 sRGB 配置文件的 8 位 PNG。

这些预览不包含浮点测量数据，也不能证明与 Photos 中的 Dolby Vision 动态修剪播放相同。测试用预处理副本引用不变的输入彩色轨道，以避免重复存储。因此，这些副本不能独立搬移。产品输出 `pending.mov` 仍是独立文件。

使用验证脚本构建的渲染器运行 HDR 色彩回归：

```bash
/absolute/path/new-results/cinematic-render-comparison \
  --verify-color /absolute/path/new-color-results
```

已知 HLG 色块必须与经过色彩管理的参考一致。此前的线性 sRGB 解释必须无法通过负对照。SDR PNG 必须包含 sRGB 配置文件，并在系统色调映射后保留可区分的高光层次。不对称角标在 `0`、`90`、`180` 和 `270` 度下必须与独立的 Core Image 参考一致。

### 解释结果

比较完成表示检查已执行。应结合 `all_compared_frames_identical` 和数值差异评估相同性。即使两份媒体都能渲染，缺失的相机标定、光学几何或原始对焦决策仍可能导致效果不同。

这些测试不能证明 Photos 保存和重新打开的行为、设备相册行为，或未采样帧的相同性。
