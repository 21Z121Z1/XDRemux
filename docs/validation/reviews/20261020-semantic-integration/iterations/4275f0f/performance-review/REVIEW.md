## Causal claims that this evidence does not support

- **Do not add nested spans twice.** HDR + area are 0.871789s within the 1.173500s scene span, leaving 0.301710s. Adding both detail spans to coarse scene overstates total time.
- **Do not equate candidate wall occupancy with CPU regression.** HDR + area + key-1 wall = **1.282785s**, numerically close to the **1.28s** median user gap. These are different sample windows and different measurements; main's corresponding work is not zero. That coincidence is not an attribution.
- **Do not assign all cost to one merge or new validation.** Several correctness changes and build/feature differences coexist. No commit-level same-runner control or baseline stage profile isolates one of them. Full Texture generation, semantic Vision processing, base encode and final validation were already present on main.
- **Do not use a prior cross-job pass/fail as a mechanism.** Earlier 4b/c379 ratios and the current +13.29% corroborate a continuing revision gap, but raw cross-job durations do not distinguish algorithm work, framework service, scheduling or machine state. This review does not infer a load-based cause.

## Smallest next prototype, if authorized

Prioritize the now-measured **0.752853s HDR reconstruction** before a new fit rewrite or a general profiling layer. First inspect optimized code for `reconstruct_scene_linear_hdr` / `apply_iso_gain_sample`: the outer function validates immutable channels/weight once, while the public scalar helper repeats those same checks per sample (`hdr/scene_linear.rs:135–165,181–207`). LLVM may already inline/hoist them. Source repetition alone is not proof of repeated machine work.

Only if optimized code retains that work, make one **audit-only** kernel prototype that reuses the already-validated immutable application within the loop. Keep the public scalar contract, per-sample/result finite and bounds checks, failure behavior, sampling, FP operations/parentheses and iteration order. Compare original/prototype interleaved with identical compiler/target and exact RGB output bytes across the public scene plus deterministic RGB/mono, gamma/headroom, boundary and invalid requests. Stop if bytes/errors differ or speedup is not clear; do not remove product assertions. A Linux kernel result would show potential only; ARM64 and the unchanged full native gate remain necessary before adoption.

The paired area's **0.118936s** is a small candidate-only ceiling for footprint reuse, not a first justification for another abstraction. No prototype is implemented or measured in this review. Even a successful kernel experiment would not establish that this kernel caused the entire main/candidate gap. The current evidence supports a bounded investigation, not an algorithm rollback, a budget change, or a claim that 91's native performance is already verified.
