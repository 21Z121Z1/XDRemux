# XDRemux Technical Writing Guide

English | [简体中文](style-guide.md)

XDRemux uses the principles of ASD-STE100 Simplified Technical English, Issue 9, for current technical documentation.

This project does not claim formal ASD-STE100 compliance. The standard is the primary reference for STE. This guide defines the project-specific terminology and publication rules that apply to XDRemux.

## Source language

English is the canonical source for current technical documentation.

Write or update the English document first. Then translate the same technical meaning into Chinese. Do not add product behavior only to the Chinese version.

Historical evidence records are an exception. Do not rewrite their measurements or conclusions to make them match current behavior.

## Required writing rules

Use these rules for user guides, CLI references, developer guides, model cards, test policies, and agent runbooks:

1. Use one technical noun for one item.
2. Use one technical verb for one action.
3. Prefer active voice.
4. Put one main instruction or fact in each sentence.
5. Use short sentences when a longer sentence can be split without loss of meaning.
6. Put conditions before the action when the condition controls the action.
7. Use `must` for a requirement, `can` for a capability, and `may` for a possibility.
8. Do not use marketing words such as *seamless*, *smart*, *easy*, or *high quality* unless a measured definition follows.
9. Do not replace an exact technical term with a casual synonym.
10. Keep code identifiers, metadata keys, command options, file names, and standard names unchanged.
11. Define an abbreviation at first use unless it is a common project term in the glossary below.
12. Separate verified behavior from hypotheses, research observations, and device-dependent results.

## Project terminology

Use these terms consistently:

| Term | Meaning |
| --- | --- |
| `ProXDR` | The vendor HDR photo format that XDRemux converts to standardized HDR HEIC. |
| `Gain Map` | The auxiliary image and metadata used to reconstruct HDR from a base image. |
| `Motion Photo` | An Android photo asset that contains a still image and motion-video data. |
| `Live Photo` | The Apple HEIC + MOV asset pair that shares one asset identifier. |
| `cover-frame PTS` | The presentation timestamp that identifies the source cover frame. |
| `still-image-time` | The Apple timed-metadata value that identifies the Live Photo still frame. |
| `compressed-sample passthrough` | Copying encoded video or audio samples without decoding and re-encoding them. |
| `OPPO-compatible output` | The optional output mode selected by `--oppo-compatible` or related compatibility controls. |
| `Photographic Styles` | Apple Photos style-editing data generated by the Apple feature pipeline. |
| `Apple Portrait` | Apple Photos portrait-editing data generated from compatible source depth resources. |
| `fixture` | A versioned input file used by an automated test. |
| `historical record` | A dated audit, experiment, or evidence note that describes repository state at a specific time. |

Do not use *live picture*, *dynamic photo*, or *motion image* as synonyms for `Motion Photo` or `Live Photo` in normative documents.

## Document classes

### Current normative documents

These documents describe current behavior or current maintenance rules. Keep them in English and Chinese.

Examples include the root README, CLI reference, Apple feature guide, development guide, quality policies, validation runbook, test README, fixture README, model cards, and agent acceptance rules.

### Historical records

A historical record can contain old paths, old measurements, or conclusions that applied only to one repository state.

Do not rewrite the body of a historical record to make it current. Add or maintain a separate current summary when readers need one.

### Generated or code-owned text

Command output, error strings, metadata keys, JSON fields, and source-code identifiers are code-owned text. Documentation must reproduce them exactly when exact spelling is important.

## Translation rules

The Chinese version must keep the same technical scope as the English version.

Keep these items in their original form unless a well-established Chinese technical term improves clarity:

- file formats and standards;
- API and framework names;
- command options;
- code identifiers;
- metadata keys;
- path names;
- measurement units.

Translate the explanation, not the identifier.

## Review checklist

Before a documentation change is complete:

1. Check every behavioral statement against current code, tests, or a current validation result.
2. Check that the English and Chinese versions have the same requirements and limitations.
3. Check all local links.
4. Check command examples against the current parser.
5. Mark device-dependent behavior as device-dependent.
6. Do not convert a historical observation into a current product guarantee.
