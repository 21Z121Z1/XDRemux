# Lead judgment

Read the source and judge each finding against the actual goals. The number of findings or reviewers does not decide whether a change is necessary.

## Check reachability and evidence

If validation or ownership demonstrably prevents a hypothetical input, dismiss that finding. Identify the relevant boundary before making this judgment. A type alone does not validate arbitrary media bytes, helper output, persisted data, or native facts.

Ask for a concrete caller, failure, maintenance cost, or lost contract. Preferred abstractions, style choices, file length, and confident wording do not establish a correctness defect. Keep simple code when added indirection would not reduce an owned obligation.

Compare apparent context gaps with canonical constraints. Support each dismissal with evidence. Do not dismiss a security or correctness issue because only one reviewer found it. Another reviewer's silence does not invalidate the finding. Independent agreement is useful supporting evidence, but it does not prove the claim.

## Decide what to do

Retain a finding if it demonstrates an execution path, disproves an assumption, or exposes a material contract or evidence gap. Assign Act on, Consider, Noted, or Dismissed. Give a short reason.

Fix only accepted issues within the authorized scope. Rerun the affected checks. After substantive changes, review the resulting change again.
