# Lead judgment

Do not count findings or reviewers as votes for a change. Read the source and decide whether each finding describes a reachable problem within the actual goals.

Dismiss a hypothetical input when validation or ownership demonstrably prevents it. A type alone does not prove arbitrary media bytes, helper output, persisted data, or native facts valid. Find the relevant boundary before making that judgment.

Do not treat a different preferred abstraction, style choice, file length, or confident tone as a correctness finding. Request a concrete caller, failure, maintenance cost, or lost contract. Keep simple code when added indirection would not reduce an owned obligation.

Inspect apparent missing-context findings against canonical constraints. Explain a dismissal with evidence. Do not dismiss a security or correctness issue merely because only one reviewer found it, or because another reviewer was silent. Independent agreement is useful supporting signal, not proof.

Retain a finding when it identifies a demonstrated execution path, invalidates an assumption, or exposes a material contract/evidence gap. Assign Act on, Consider, Noted, or Dismissed with a short reason. Fix only accepted in-scope issues, rerun the affected evidence, and revisit the reviewed result after substantive changes.
